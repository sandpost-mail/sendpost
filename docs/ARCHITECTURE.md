# Sandpost Architecture (draft v0.1)

Companion to [PRD.md](./PRD.md). Stack: Go, Svelte, Postgres. One binary, stateless, horizontally scalable.

## 1. Overview

```
 apps / CI                         browsers / CI / scripts
    |  SMTP (AUTH)                        |  HTTPS
    v                                     v
+-----------+   +----------------------------------------------+
| SMTP      |   | HTTP server                                  |
| listener  |   |  /ui (embedded Svelte)  /_/api/v1 (native)   |
| (go-smtp) |   |  /api/v1 (Mailpit compat, project-scoped)    |
+-----+-----+   +----------------------+-----------------------+
      | project resolved by credential |  user/token + RBAC
      v                                v
+---------------------------------------------------------------+
| Core services: ingest, projects, access, search, policy,      |
| delivery, events, audit                                       |
+--------------------------+------------------------------------+
                           |
                     +-----v-----+        +--------------------+
                     | Postgres  |        | outbound SMTP      |
                     | (+LISTEN/ |        | (SES, generic)     |
                     |  NOTIFY)  |        +--------------------+
                     +-----------+
```

All instances run all components. Scaling is adding replicas behind a TCP load balancer for SMTP and an HTTP ingress for the UI and API.

## 2. Components

### 2.1 SMTP listener
- Library: `emersion/go-smtp`.
- AUTH PLAIN and LOGIN only. TLS or STARTTLS from config. A connection without successful AUTH can not submit mail (reject at `MAIL FROM`).
- On AUTH, the credential is looked up by username. SMTP secrets are generated by the server (long and random, never user-chosen), so they are stored as an HMAC-SHA256 keyed with the server key and compared in constant time. No slow hash and no verification cache are needed, because high-entropy secrets can not be brute-forced. Failed attempts are rate limited per source IP.
- The authenticated credential fixes the `project_id` for the session. Nothing in the message (recipient, headers) can change which project receives it.
- DATA is read into memory up to a global max size (`MAX_MESSAGE_BYTES`), then handed to ingest.

### 2.2 Ingest
1. Parse with `enmime`: headers, text, HTML, attachments, inline parts.
2. Insert the message in one transaction: raw bytes, parsed fields, recipients, attachment metadata, extracted links.
3. Apply tag rules (for example `X-Run-Id` header to tag).
4. `NOTIFY` on a per-project channel so every replica can push to its connected UI clients and wake long-poll waiters.
5. Hand over to the policy engine (async, after commit).

Capture always succeeds before any outbound action is attempted.

### 2.3 Policy and delivery engine
Per project: one optional transport and one policy.

Policy modes: `capture` (default), `allow`, `redirect`.

For each recipient (To, Cc, Bcc) the engine decides:
- matches allowlist: deliver to the real address
- else, mode `redirect`: replace with the project redirect address
- else: do nothing

Rules the engine enforces:
- Rewrite the SMTP envelope, not only the headers. Bcc is not carried into the delivered message.
- Allowed and redirected recipients are sent as separate deliveries, so a real recipient never sees the redirect headers and vice versa.
- Redirected messages carry `X-Original-To`, `X-Original-Cc` and an optional subject prefix.
- Fail closed: if the policy cannot be evaluated, the transport is missing or disabled, or a recipient fails parsing, nothing is sent and the failure is logged on the message.
- Each outbound attempt is recorded in `deliveries` (status, recipient, error), with bounded retries driven by a Postgres-backed job queue ([River](https://github.com/riverqueue/river), MPL-2.0, used unmodified as a dependency). No Redis.
- Transport secrets are encrypted with an application key (`SECRET_KEY`, AES-GCM). Key rotation is a documented procedure.
- Manual release uses the same engine, with an explicit target address that must pass the allowlist.

### 2.4 HTTP layer
- Router: `chi`. OpenAPI generated or checked in CI.
- **UI session auth**: cookie session, CSRF protection, argon2id passwords (human passwords only).
- **Token auth**: user tokens and project tokens, server-generated, stored as HMAC-SHA256 and prefixed for secret scanners.
- **Native API** `/_/api/v1/...`: projects, users, groups, credentials, policy, messages, comments, tokens, audit.
- **Compatibility API** `/api/v1/...`: Mailpit-shaped endpoints scoped to one project. The project is resolved from a project API token, sent as a Bearer token or as the Basic auth password (any username). A client therefore only changes its base URL and auth. An optional `/p/{slug}/api/v1/...` alias gives an explicit-URL form.
- **Events**: SSE only, for the UI and live clients. No WebSocket endpoint.
- **CI endpoints**: `GET .../wait?to=&subject=&timeout=` long-poll, `.../extract` for links and codes.

### 2.5 Authorization
- Central `authz` package. Every query that touches project data goes through a project-scoped repository that requires a `ProjectID` argument and a checked permission. No handler queries messages directly.
- Role matrix:

| Capability | Viewer | Member | Owner | Instance admin |
|---|---|---|---|---|
| Read messages | yes | yes | yes | yes |
| Delete, tag, comment | no | yes | yes | yes |
| Manage credentials, policy, transport | no | no | yes | yes |
| Manage groups on project | no | no | yes | yes |
| Manage users, create projects | no | no | no | yes |

- A user's effective role on a project is the highest role among their groups assigned to it.
- The project representation (`GET /projects`, `GET /projects/{id}`, and the create response) carries `role`, the caller's effective role: viewer, member or owner. It is resolved by `authz.UserRole` (group rank, instance admin flag, token ceiling), the same function the guard uses, so what the UI shows is what the server enforces. Administrators are owners, a token caller gets the role capped by its scopes. The list resolves roles in the same query that selects the visible projects (highest rank per project), so there is no query per project, and a project without a role is never listed.
- Tests: a table-driven authorization suite plus a cross-tenant leakage test that tries every endpoint with another project's identifiers.

### 2.6 UI (Svelte)
- SvelteKit in SPA mode (static adapter), embedded with `go:embed`.
- Views: project switcher, inbox list with search and filters, message detail (HTML, text, source, headers, attachments, links), live updates, comments, message permalink, project settings (credentials, policy, tokens), admin (users, groups, audit).
- The HTML preview renders in a sandboxed iframe with a strict CSP, and remote content is blocked by default.

### M1 implementation notes
- HTTP routing uses the standard library `ServeMux` (Go 1.22 patterns), not chi, until a need appears.
- `messages.search` is a generated tsvector over the body only (truncated to 200k characters, `simple` config). Subject, sender and recipients use `pg_trgm` GIN indexes with ILIKE.
- Attachment rows hold metadata and an `ordinal`. Bytes are re-parsed from `raw` on download.
- The event bus keeps one dedicated connection per replica, LISTENs on `sp_msg_<projectID>` only while a local subscriber exists, and sends `resync` after a reconnect. `NOTIFY` is issued inside the ingest transaction, so it fires only on commit.
- The SPA is built into `internal/webui/dist` (placeholder only in git) and embedded. The HTML preview is served by `/_/api/v1/projects/{id}/messages/{id}/html` with a sandbox CSP (no scripts, remote images blocked).
- The native API was unauthenticated until M2. That is resolved, see the M2 implementation notes below (the inline attachment URLs of the sandboxed preview are now signed).

### M2 implementation notes

Authentication
- Two credentials reach the native API: a browser session (cookie `sandpost_session`, or `__Host-sandpost_session` while `COOKIE_SECURE` is on, which is the default) and a bearer API token. A Bearer header always wins and never falls back to the cookie. A request with neither gets 401.
- Login (`POST /auth/login`) verifies argon2id (a dummy hash is verified for unknown emails, so timing does not reveal accounts) and creates a session. The cookie holds 256 random bits, only its HMAC is stored in `sessions.id`. Sessions last 24 hours, absolute. Disabling a user, resetting its password, or the user changing its password ends its other sessions.
- The cookie is `HttpOnly`, `SameSite=Strict`, `Path=/`, and `Secure` unless `COOKIE_SECURE=false`. The default is true: it suits HTTPS (also behind a TLS terminating proxy) and `http://localhost`, which Chrome, Firefox and curl treat as a secure context. Safari and plain http on other host names drop Secure cookies, so those setups need `COOKIE_SECURE=false` (the `make dev` targets default to it). Failed logins are limited per source address (20 per 5 minutes) and per account name (10 per 5 minutes), then 429 with `Retry-After`. At most 4 password checks run at once (each argon2 verify uses 64 MiB) and the limit is checked again after getting a slot, so parallel guesses can not slip past it. Behind a proxy all clients share the proxy address, the account limit still applies.
- CSRF: every unsafe request authenticated by cookie must carry `X-CSRF-Token`. The token is derived as an HMAC of the session id with its own key (nothing stored) and is returned by login and `GET /auth/me`. Bearer requests do not need it. Writes must also be `application/json`, so plain cross site form posts never reach a handler.
- `must_change_password` (set by the bootstrap admin, user creation and password resets) limits the user to `GET /auth/me`, `POST /auth/password` and `POST /auth/logout`. Everything else answers 403 with code `password_change_required`. Changing the password is for browser sessions only, so a leaked token can not take over an account.
- Machine credentials follow M1: API tokens are `spu_` (user) or `spp_` (project) plus 256 random bits, stored as an HMAC under their own derived key, with the first 12 characters kept for display. They are shown once at creation and can be revoked. A token never carries more power than its owner: user token scopes are `read` (viewer ceiling), `write` (member ceiling) and `manage` (no ceiling). Project tokens are pinned to one project, accept `read` and `write` only, and are capped at member even if a row says otherwise. A token can only mint tokens within its own scopes. Tokens of a disabled user stop working at once.

Authorization
- `internal/authz` holds the role matrix (viewer, member, owner, plus admin), the effective role (highest role among the user's groups on the project, one SQL query, admins are admin everywhere, token scopes cap it), and `Scope`, a value that can only be obtained by passing a capability check (`Authorizer.Project`), by verifying a signed grant, or with `authz.Trusted` for paths that were authorized differently (the SMTP credential fixes the project of a session, and test setup). The messages, credentials, projects (tag rules), groups (role assignment) and tokens (project tokens) services take a `Scope`, never a bare project id. Child ids (message, credential, rule, token) are always resolved with `project_id` in the SQL `WHERE`.
- All native routes are declared once in `internal/api/routes.go` with an access kind (`public`, `any`, `user`, `global`, `project`, `signed`) and a capability. One guard enforces them, handlers never decide access. The authorization matrix test, the leakage suite and the OpenAPI check all iterate over that table, so a new route without a fixture or a spec entry fails CI.
- Status policy: 401 not authenticated. 404 for anything missing or not visible, with a body identical to a missing project, so ids can not be probed. 403 when the caller can see the project but lacks the capability. Lists are filtered (`GET /projects` returns only visible projects).
- Capabilities (see 2.5): `messages.read` viewer (this includes marking a message read and the event stream), `messages.write` member, `project.manage` (credentials, tag rules, project tokens) owner, `project.groups` (role assignment, project audit) owner, and the global `users.manage`, `groups.manage`, `projects.create`, `audit.read` for administrators. The last active administrator can not be demoted or disabled.

Sandboxed preview and SSE
- The preview iframe has an opaque origin and carries no cookie. `GET .../messages/{mid}/preview-url` (needs `messages.read`) returns a URL with `grant=<expiry>.<signature>`, valid 5 minutes. The signature is an HMAC under a key derived from `SECRET_KEY` and binds project id, message id, resource (`html` or `attachment/<ordinal>`) and expiry. The HTML response rewrites `cid:` references to attachment URLs carrying their own grants. A grant is only honoured by the `html` and `attachments` routes, only for GET, and a replay on other ids or resources gets 404. The responses send `Referrer-Policy: no-referrer`.
- The event stream authorizes before subscribing, so no `LISTEN` is opened for an unauthorized caller. A stream of a browser session ends when the session expires.

Audit
- Admin actions write `audit_log` rows in the same transaction as the change (user, group, membership, project, role assignment, credential, tag rule and token actions). The actor travels in the request context. `detail` never holds secrets. `GET /audit` (administrators) and `GET /projects/{pid}/audit` (owners) page with a cursor.

API shape for the UI (item 2.8)
- Login: `POST /auth/login` returns `{user, csrf_token, expires_at}`. If `user.must_change_password` is true, show the password form (`POST /auth/password`) and nothing else. Store `csrf_token` in memory and send it as `X-CSRF-Token` on every non GET. After a page reload call `GET /auth/me` to get it back, a 401 means show the login page.
- Errors are `{error, code?}`. Codes the UI branches on: `unauthenticated`, `csrf_invalid`, `password_change_required`, `invalid_credentials`, `too_many_attempts`.
- Lists are `{items: [...]}`, paged lists (messages, audit) add `next_cursor` (empty on the last page).
- Secrets (SMTP credential secret, token secret) appear only in the creation response.
- The OpenAPI document is `docs/openapi.yaml`. It is hand written, `make openapi` (and the `openapi` CI job) checks it against the registered routes and lints it.
- The SPA implements this (item 2.8), see the M2 UI notes below.

M2 UI notes (item 2.8)
- Session: the root `+layout.ts` calls `GET /auth/me` once per page load (`SessionStore`, `lib/session.svelte.ts`), keeps the CSRF token in memory only, and redirects with the pure rule in `lib/guard.ts`: anonymous goes to `/login?next=...`, a pending password change goes to `/change-password`. The root layout re-applies the rule reactively, so an expired session, a sign out elsewhere or a `password_change_required` answer from any call moves the user without a reload. Child loads call `await parent()` so nothing runs unauthenticated.
- `lib/api.ts` sends cookies (`same-origin`) and `X-CSRF-Token` on every non GET, exposes `ApiError.code`, and reports 401, `password_change_required` and `csrf_invalid` to hooks wired in the session store (401 signs out locally, `csrf_invalid` refetches the token). Login and `me` handle their own 401.
- Access: every project from the API carries the caller's `role` (see 2.5), and `lib/access.ts` maps it to what the UI needs: `owner` (Settings, Audit, credentials, tokens, group roles) and `canWrite` (member and owner, for message actions that need `messages.write`, such as comments since M5.5). Viewers can still read and mark messages read. The project layout reads the role from `GET /projects/{id}`, so there is no probing and no expected 403 in the browser console. The server enforces everything, hiding is for usability.
- Signed preview: the message page fetches `GET .../preview-url` when the HTML tab opens and uses the returned URL as the iframe `src`. Attachment and raw downloads are plain links (the cookie is sent). The SSE stream uses the cookie, and a closed stream triggers a session check.
- Owners without `groups.manage` cannot list groups, so the project Access section lets them assign a group by numeric id, administrators get a select.
- Tests: Vitest with jsdom and Testing Library (`cd web && npm test`, run in the CI web job). Covered: API client, guard, validation, role mapping, session store, login, password and token components.

Decisions taken here (revisit if needed)
- Marking a message read is a `messages.read` capability, so viewers can do it (it is shared state, but a read only role would make opening a message fail).
- Project owners can assign any existing group (by id) to their project, not only groups they can see. An owner can probe group ids that way.
- Session lifetime is a fixed 24 hours, there is no sliding window or "remember me".
- Account recovery is `sandpost admin` (`list-users`, `create-admin`, `reset-password`, `unlock`, `promote`, see README). It connects with `DATABASE_URL` through the same config loader and uses `users.Service`, so validation, the last administrator guard, session revocation and audit rows are the ones of the API. Passwords come from a no echo prompt or `--password-stdin`, never argv. CLI changes carry no actor user: `audit.WithSource(ctx, "cli")` records `"actor": "cli"` in the audit detail. `unlock` clears `disabled_at` only: login throttling lives in process memory, nothing is persisted, so restarting the server clears it.

### M3 implementation notes

Contract and routes
- Target Mailpit v1.31.6. Its swagger (OpenAPI 2.0) is vendored unmodified in `docs/mailpit/`, tests read it from disk. `docs/MAILPIT_COMPATIBILITY.md` is the endpoint matrix, `docs/MAILPIT_MIGRATION.md` the guide.
- The compat handlers live in `internal/api` (`compat_*.go`) rather than in a separate `mpcompat` package: they share the server, its dependencies and the test harness. They have their own route table (`compatRoutes`, exported as `CompatRoutes()`), separate from the native one, so `docs/openapi.yaml` and its test only cover `/_/api/v1`. `compat_contract_test.go` ties the table to the vendored swagger (every operation present, none extra) and to the matrix document.
- Routes are registered twice, `/api/v1/...` and `/p/{slug}/api/v1/...`, plus `/view/{name}` and `/p/{slug}/view/{name}` (Go patterns can not express `{ID}.html`, the handler splits the suffix). `/api/v1/` and `/p/{slug}/api/v1/` have a catch-all answering Mailpit's plain `404 page not found`, so unknown paths never fall through to the SPA. Endpoints Sandpost does not offer are in the table as `unsupported` and answer 501 after authentication.

Authentication and authorization
- `compatGuard` is separate from the native `guard`: only `Authorization` is read (Bearer, or Basic with the token as password), never the session cookie, so no CSRF handling is needed and `requireJSONWrites` is not applied (Mailpit clients send DELETE without a body or content type). Tokens are verified by `tokens.Service`, a user whose `must_change_password` is set gets 403.
- Project resolution: a project token names its project (`Authorizer.Project` on its own id). A user token must use `/p/{slug}`, resolved by the new `Authorizer.ProjectBySlug`, which returns `ErrNotFound` for an unknown slug exactly like for a project without a role. All three cases produce the same 404 body and headers (tested).
- Capabilities: `messages.read` for reads and for marking read (also `GET /message/{ID}` and the views, which mark read as Mailpit does), `messages.write` for delete and tag changes.
- All data access goes through `messages.Repository` methods that take an `authz.Scope`, and every new SQL statement restricts `project_id` itself. Ids in request bodies are intersected with the project in SQL (`project_id = $1 AND id = ANY($2)`), so a foreign id is silently ignored, the answer equals the one for an unknown id. `messages.New` now takes a `store.DB` (it needs transactions for tags).

Search
- The Mailpit syntax is parsed by `search.ParseMailpit` into a `search.Filter`: parallel slices (kind, value, negate) with LIKE patterns already escaped. It is separate from the native `search.Parse` because it needs negation, repeated keys and more operators.
- Migration `00005_compat_search.sql` adds the SQL function `sp_filter_match(id, from, subject, message_id, text, read_at, received_at, size, headers, kinds, vals, negs)` (columns, not the row, so raw and html_body are never detoasted; queries skip the call when the filter is empty; at most 20 terms): a message matches when every term holds (a term holds when its match differs from its negate flag, an unknown kind never holds, so mistakes fail closed). The list, count, delete and set-read queries (`store/queries/compat.sql`) share it, so a search used for deletion selects exactly what the same search lists. The function reads only the row it gets, queries always add `project_id`.
- Destructive operations by search (`DELETE /search`, `PUT /messages` with `Search`) refuse a filter with no usable term (400) and an invalid date is a 400 instead of Mailpit's silently dropped term, so a typo can not widen a delete. `DELETE /messages` with an empty body or list deletes everything of the project (as Mailpit), a malformed body is a 400.
- Free text is a substring match (ILIKE) over subject, text body, sender and recipient addresses, as Mailpit does. It does not use the tsvector index, so on very large mailboxes it is a scan inside the project. Pagination is offset based (`start`/`limit`, `limit=0` meaning "all" is capped at 1000), as the contract defines.

Shapes
- `compat_shapes.go` maps stored data to Mailpit JSON: ids as decimal strings, `PartID` is the attachment ordinal, display names come from the stored headers (`To`, `Cc`, `Reply-To`), `Bcc` is the envelope recipients missing from To and Cc, `Snippet` is derived from the body at read time (the first 1000 characters of text, or 4000 of HTML when there is no text), attachment checksums are computed from the raw message when a message is fetched. `Username` is empty (the SMTP credential is not stored on messages).
- Tags: a project's tag list is derived from `message_tags`, unused tag rows are pruned after deletions and tag changes (`FOR UPDATE SKIP LOCKED`, so a concurrent ingest that has just upserted a tag is never raced). Tag names follow Mailpit's rule (letters, digits, space and `- _ . @`, at most 100), invalid names are dropped. Migration `00006` makes tag names unique without regard to case (`lower(name)`, merging existing variants), `UpsertTags` conflicts on it and inserts names in sorted order so concurrent writers can not deadlock.

Not done
- Thumbnails (image decoding of untrusted input, no resize dependency), send, chaos (release came with M4), HTML/link/SpamAssassin checks. Deleting through this API does not publish an event on the SSE stream yet.
- Running real Mailpit client libraries and Mailpit's own examples against Sandpost (backlog 3.4) needs network access and their toolchains, it is open.

### M4 implementation notes

Packages
- `internal/policy`: the engine, pure functions (no database, network or clock). `Evaluate` (policy run after capture) and `EvaluateRelease` (manual release) return a `Plan`: one `Decision` per original recipient and at most one allowed and one redirected `Outbound`. `Outbound` has private fields and can only be built by those two functions. `internal/delivery.Relay.Send` accepts nothing else, so an address that did not pass the engine can not reach the wire.
- `internal/delivery`: transport and policy settings, manual release, delivery rows, the River worker and the SMTP relay client. `internal/secrets`: AES-256-GCM for relay passwords. `internal/testutil/relay.go`: a fake SMTP relay for tests.

Engine rules (all covered by table driven tests, `internal/policy`)
- The recipient set is the SMTP envelope (`RCPT TO`, stored as `message_recipients` kind `envelope`), not the headers. Header To and Cc are only used to fill `X-Original-To` and `X-Original-Cc` on redirected mail.
- Fail closed means `*BlockedError` and an empty plan. Blocking cases: unknown or empty mode, no transport, transport disabled, invalid transport sender, any invalid allowlist entry (the whole list is rejected), missing or invalid redirect address in redirect mode, subject prefix with control characters or over 100 characters, no envelope recipient, and any envelope recipient that does not parse. One bad recipient blocks the whole message, because a recipient the engine can not read is one it can not classify. Capture mode (or no policy row) never sends and never blocks.
- Addresses are validated strictly (`policy.ParseAddress`): plain `local@domain`, ASCII only, dot-atom local part without `% ! |`, at least two labels, no IP literals, no display names, no quoted local parts, no comments, at most 254 characters. The domain is lower cased.
- Allowlist entries are `user@example.com`, `@example.com` or `example.com`. Matching is case insensitive and exact: no wildcards, and `@example.com` does not include subdomains. An empty allowlist is valid (allow mode sends nothing, redirect mode redirects everything).
- Allowed recipients go in one message, all redirected recipients in a second one with the single redirect address as envelope recipient, so neither side sees the other's headers. The second one carries `X-Original-To`, `X-Original-Cc` and the subject prefix (RFC 2047 encoded when not ASCII).
- Header rewriting touches only the top level header block: `Bcc` and any `X-Original-*` (also `X-Original-Bcc`) are removed from every outbound message (sender supplied ones can not be trusted or leak), everything else and the body are kept byte for byte, with the original line endings.
- Envelope sender: the original MAIL FROM is not stored, so the engine uses the transport's `sender` (validated) or the null sender. Bounces therefore never reach a real mailbox by default. Amazon SES needs a verified sender, the `ses` kind requires one.
- Manual release needs a stored policy (its allowlist is the gate, whatever the mode), an enabled transport and every target on the allowlist. One refused target refuses the whole release, nothing is queued. It does not widen anything in redirect mode. Release is allowed in capture mode on purpose: it is an explicit action by a member and still limited to the allowlist.

Data
- Migration `00007_delivery.sql`: `transports` (one per project, kind `smtp` or `ses`, TLS mode `starttls`, `implicit` or `none`, `sender`, `enabled` false by default), `delivery_policies` (mode, allowlist jsonb, redirect address, subject prefix) and `deliveries`. The engine validates policy data again on every send, so rows written around the API still fail closed (the e2e test injects them with SQL).
- `deliveries` has a `project_id` (not in the early sketch of section 3): every query filters on it and the worker loads the message with `project_id` in the `WHERE`. One row per original recipient and run, unique on `(message_id, run, recipient)`. `run` is `auto` (the policy run after capture) or `release:<id>`. Kinds `deliver`, `redirect`, `release`, `skip`, `blocked`, statuses `pending`, `sent`, `failed`, `skipped`, `blocked`. A run the engine refused gets its pending rows set to `blocked` plus one row with an empty recipient holding the reason. Redirected recipients share the outcome of the one redirect message.
- Transport passwords are sealed with AES-256-GCM. The key is `HMAC-SHA256(SECRET_KEY, "sandpost/transport-secret/v1")`, the nonce is random and the additional data is `transport:<project id>`, so a blob copied to another project does not open. Format: version byte, nonce, ciphertext. Passwords are never returned (`has_secret` only), never put in audit details, job arguments or logs (`RelayConfig` redacts itself in `fmt` and `slog`).
- Key rotation: the key is a function of `SECRET_KEY`, so after changing it every stored transport password fails to open and delivery fails closed (the run is blocked with "password can not be decrypted", the connection test says so). Procedure: change `SECRET_KEY` (this also invalidates SMTP credentials and API tokens, see the PRD), restart, and have each project owner enter the relay password again in Settings. There is no online re-encryption.

Jobs (River)
- River runs on the same Postgres, no Redis. Its tables come from River's own migrator, run by `store.MigrateUp` right after the goose migrations (`sandpost migrate up` leaves one complete schema, `migrate status` lists River's versions as `river:<name>`). `migrate down` rolls back goose migrations only. A test asserts that nothing is pending after `MigrateUp`. River v0.49.0 is pinned.
- Ingest queues the job in the capture transaction through `ingest.Hook` (`delivery.Enqueuer`), only when the project's policy mode is not capture. The hook runs in a savepoint: if it fails the savepoint is rolled back, the failure is logged and the message is still stored (tested with a failing queue). A crash can not leave a committed message without its job, and a failed enqueue never loses mail.
- Every attempt re-reads the message, recipients, policy and transport and runs the engine again before the first SMTP command. Nothing persisted from an earlier attempt authorizes a send, so switching a project to capture, narrowing the allowlist or disabling the transport stops mail that is still queued (tested). A blocked run ends without retry. The job arguments carry ids (and the normalized targets of a release), never message content or secrets.
- Retries are bounded: `MaxAttempts` is 5 with River's default backoff (about 1s, 16s, 81s, 4m). An SMTP 5xx answer for a recipient, a TLS or certificate problem and a missing STARTTLS are permanent (the row fails at once, the job does not retry for it). 4xx answers, network errors and timeouts are transient: the row stays `pending` with the error text and `attempts`, only pending recipients are tried again, and after the last attempt they become `failed` ("gave up, retries exhausted"). Delivery is at least once: a crash between the relay accepting a message and the row update can send it twice.
- The job timeout is 3 minutes, 4 workers per process.

SMTP relay client (`delivery.SMTPRelay`, emersion/go-smtp)
- TLS modes: `starttls` fails when the relay does not offer STARTTLS (it never downgrades), `implicit` is TLS from the first byte, `none` is plaintext and can not be combined with a username (the client refuses to send credentials without TLS, and the API refuses to store them). Certificates are always verified against the system roots, with TLS 1.2 as minimum, there is no option to skip verification. The password is only sent after the secured session exists.
- AUTH PLAIN, or LOGIN when only that is offered. One `MAIL FROM`, one `RCPT TO` per envelope recipient with a per recipient result (a refused recipient does not stop the others), then DATA. When every recipient is refused no DATA is sent.
- Relay text stored in `deliveries.error` is cleaned: control characters removed, the password masked if echoed, 300 characters at most.
- Connection test (`POST .../transport/test`): connects, secures, authenticates, NOOP, QUIT, sends no mail. It only tests the stored settings, never unsaved ones. Its error text is built from the failed step and the SMTP code only, never from what the remote host said, so it can not be used to read banners.
- Changing the connection settings (kind, host, port, username, TLS mode) of a transport disables it again and requires the password to be entered again. Together with "test uses stored settings", this means the stored password can only ever be sent to the host the owner saw it saved for (and that they re-confirmed with the password). A new transport starts disabled and `enabled` is ignored on creation.
- A project owner chooses the relay host, so the connection test and the delivery job connect to an address the owner picks, including internal ones. This is deliberate (relays on private networks are the common case) but it is an SSRF surface: only owners can do it, only SMTP is spoken, remote text is not echoed. Restricting target ranges can be added as a deployment option later.

API and authorization
- Native routes (all in `routes.go`, so the authorization matrix, leakage suite and OpenAPI check cover them): `GET|PUT|DELETE /projects/{pid}/transport`, `POST .../transport/test`, `GET|PUT .../policy` (all `project.manage`, owners), `GET .../messages/{mid}/deliveries` (`messages.read`), `POST .../messages/{mid}/release` (`messages.write`, answers 202 with the pending rows, 400 with code `delivery_blocked` and the reason when the engine refuses). A message id of another project answers 404 like an unknown one, for both message routes.
- Release needs `messages.write` (member) rather than owner: a member can only send to addresses the owner put on the allowlist, and CI tests that release with a project token (capped at member) keep working. Mailpit's `POST /api/v1/message/{ID}/release` uses the same service (body `{"To": [...]}`, answers `ok`, 400 with the reason, `latest` supported) and replaces the former 501.
- Audit: `transport.update` (kind, host, port, TLS mode, enabled, whether a username exists and whether the password changed, never the password or username), `transport.delete`, `policy.update` (mode, allowlist, redirect address) and `message.release` (targets).

UI (item 4.6)
- Project settings (owners) has a Delivery section: transport form (generic SMTP and an Amazon SES preset, password field that never shows the stored value and is required again when the connection changes, enable and disable with confirmation, connection test with its result) and the policy form (three modes with plain explanations, allowlist textarea, redirect address and subject prefix). `lib/delivery.ts` turns the form state into explicit warnings: nothing is sent (no transport, disabled, empty allowlist, no redirect address), real mail will be delivered to the allowlist, whole domains are allowed, the redirect target receives everything else. Saving a policy that can send real mail asks for a confirmation that lists the allowlist.
- Each message has a Delivery tab: one row per recipient with status, redirect target, error and attempts (it refreshes while something is pending), and for members and owners a release form that asks for confirmation before it queues. Viewers see the status only.

### M5 implementation notes: wait, extract, run isolation (5.1 to 5.3)

Routes (both `accessProject`, capability `messages.read`, so viewers and `read` tokens can use them, in `internal/api/wait.go` and `extract.go`)
- `GET /projects/{pid}/wait`: long poll. Query: `q` (message search syntax), `run`, header `X-Run-Id`, `after_id` (default 0), `count` (1 to 50, default 1), `timeout` (seconds, 0 to 120, default 30, 0 checks once). Answer is always 200 once authorized: `{"messages": [MessageSummary...], "timed_out": bool}`, oldest first, at most 200. `timed_out` is true when fewer than `count` matched, `messages` then holds the partial result. Bad parameters are 400, a foreign or unknown project is the usual 404 (before any subscription is opened).
- `GET /projects/{pid}/messages/{mid}/extract`: `{"message_id", "links": [string], "codes": [{"value", "kind"}]}`. Optional `link` (case insensitive substring filter on links) and `code_pattern` (RE2, 200 bytes at most, a bad one is 400). The message is read through the scoped repository (`Get` with the scope), so another project's message id is a 404.

Wait semantics
- It is a loop of "query, then wait for an event": the handler subscribes to the project's bus channel, waits for `Ready` (LISTEN live), then runs the match query, and re-runs it on every `message.created` or `resync` event (queued events are drained so a burst costs one query). A message committed between the subscription and the first query is in the query result or arrives as an event, never missed. A slow consumer or a reconnect produces `resync`, which only triggers one more query, so the poll needs no gap handling of its own.
- Messages received before the call count (the CI order is "send mail, then wait"). `after_id` is the resume cursor: pass the highest id already handled. There is no server side state, so any replica can answer and a reconnecting client loses nothing.
- Timeout is capped at 120 s and by the principal's own expiry (a session or token ending ends the poll). The HTTP server has no write timeout, so a long poll is not cut. Proxies in front must allow it (the SSE endpoint has the same requirement). Cancelled requests close the subscription.
- Match query: `messages.Repository.Match` (`internal/store/queries/wait.sql`, `MatchMessages`) repeats the `ListMessages` filters and adds `id > after_id`, the run filter and `ORDER BY id ASC`. It always filters on `project_id`, like every other query. The filter block is duplicated because sqlc has no fragments: a change to the search filters must be made in both queries.

Run isolation (5.3)
- A run id is 1 to 100 bytes of valid UTF-8 without control characters or surrounding spaces. Given as header `X-Run-Id` or query `run` (both allowed when equal, otherwise 400), it restricts `wait` to messages that carry an `X-Run-Id` header with exactly that value (header name case insensitive, any of its values), or a tag equal to the run id, or to `run:<id>` (what the README's example tag rule produces). There is no prefix matching. `q=tag:...` stays available for any other tag.
- The mechanism needs no setup: the application under test adds `X-Run-Id: $CI_RUN_ID` to its outgoing mail and the test calls `wait` with the same id. Isolation is between runs of one project. Between projects it is the scope, and run ids are not global: the same id in two projects never crosses (tested both ways).
- Cost: the header match is a scan of the project's messages above `after_id` (no index, no migration was added). Fine for CI projects, the per project retention and quotas that would bound it are post v1. If it ever shows up in a profile, add a GIN index on `messages.headers` or store the run id in a column at ingest.
- Not done: the run filter is not on the message list, the SSE stream or the Mailpit compatible API.

Extraction (`internal/extract`, pure functions, table driven tests)
- Links are the ones stored at ingest (`message_links`: HTML anchors first, then bare URLs, http, https and mailto, 500 at most), not recomputed.
- Codes are read from the text body (`Detail.Text`, enmime derives it from HTML when there is no text part), first 256 KiB only, URLs removed first so ids in links are not reported. Heuristic, in order: (1) after one of `code`, `otp`, `pin`, `passcode`, `password`, `token` on the same line, up to 40 characters of glue, then 4 to 8 digits, two groups of 3 or 4 digits split by a space or dash (joined: "482 913" gives `482913`), or an alphanumeric token with a digit (`AB12-CD34` gives `AB12CD34`): kind `keyword`. (2) If nothing matched, standalone 6 digit numbers not touching digits, dots, commas, slashes, colons or dashes: kind `digits`. A caller supplied `code_pattern` replaces both (kind `custom`, group 1 when the pattern has one, else the whole match). Distinct values in order of appearance, 20 at most. Go's RE2 has no backtracking, so a hostile pattern can not hang the request.
- Known limits: codes only present in the HTML part, codes on the line after the keyword (they fall to the 6 digit rule), and non Latin keywords are not found by the heuristic. Use `code_pattern` for those.

### M5 implementation notes: comments, permalink, activity (5.5, 5.6)

Comments (`internal/comments`, migration `00008_comments.sql`)
- Routes (in `routes.go`, so the matrix, leakage and OpenAPI checks cover them): `GET|POST /projects/{pid}/messages/{mid}/comments`. Reading is `messages.read` (viewer and up), writing is `messages.write` (member, owner, administrator, project tokens with `write`). No new capability. There is no edit and no delete: "author or owner" can not be expressed in the route table (handlers never decide access) and the backlog does not ask for it. Comments disappear with their message (`ON DELETE CASCADE`).
- Table `comments(id, project_id, message_id, user_id null, author_label, body, created_at)`. `project_id` is stored like on `deliveries`, every statement filters on it. `user_id` is nullable (`ON DELETE SET NULL`) because a project token has no user, and `author_label` keeps who wrote it when the user is gone: the email, or `project token <prefix>`. The API serves `author` (the label) and `user_id`. The author always comes from the authenticated principal, a body with `author` is a 400 (`DisallowUnknownFields`). Viewers therefore see colleagues' emails, as they already do in the audit of an owner.
- `InsertComment` is `INSERT ... SELECT FROM messages WHERE project_id AND id`, and the service checks the message first, so a message of another project is 404 for the POST and the GET whatever the body is (an invalid body can not be used to probe ids). Row, `comment.create` audit entry (comment id only, never the text) and the event commit in one transaction.
- Content is plain text, never HTML: trimmed, 1 to 2000 characters (code points, `comments.MaxBodyRunes`, also a `CHECK` in the table and `COMMENT_MAX` in the web client), invalid UTF-8 and control characters other than line break, carriage return and tab are rejected (NUL would fail in Postgres). It is stored and returned exactly as typed, with no pre-escaping (that would double escape). The protection is the JSON encoding and the UI rendering it as text (`{c.body}` in Svelte, no `{@html}`), both tested. The request body cap of 64 KiB still applies.
- Lists are oldest first with a numeric `after id` cursor (`{items, next_cursor}`, default 100, maximum 200).
- Event: `comment.created` with `message_id` goes over `NOTIFY` and the SSE stream (`events.TypeCommentCreated`). Consumers that wait for mail must filter on `message.created`, the UI refreshes an open thread on it.

Permalink
- The permalink of a message is its UI address `/projects/{pid}/messages/{mid}`: opening it needs a login and a role on the project (decision 4), a foreign or unknown id is the same "not found" page. There is deliberately no lookup of a message by id alone, which would be a cross tenant surface. The message page has a "Copy link" button. The login redirect keeps the deep link (`guardRedirect`, tested).

Activity (`internal/activity`)
- `GET /projects/{pid}/activity` (`messages.read`) is a feed of three kinds: `message` (received), `comment` (with a 200 character excerpt) and `release` (from `audit_log` rows with action `message.release`, targets in `detail`). It is a separate route from `/projects/{pid}/audit` (owners only, `project.groups`) because the audit `detail` holds transport, policy and credential data. The SQL selects the audit rows by that one action and reads only `targets`, it never returns the log. Adding a kind means adding it to the query on purpose.
- One SQL union with keyset order `(at, kind, id)` descending, each branch limited to the page size before the merge. The cursor is base64 of `unix microseconds|kind|id`. Items carry `message_id` (0 when a release names a message that is gone or in another project) and the subject, so every row links to the permalink.

UI
- Message page: a Comments tab (`MessageComments`, form only when the role is member or owner, which `canWrite` in `lib/access.ts` now serves), Copy link. New project page `/projects/{id}/activity` (nav link "Activity" for every role). The inbox stream passes non `message.created` events to open threads through `Inbox.liveVersion`.
- Tests: Vitest for the component (plain text rendering of markup, length limit, paging, viewer without form, live reload), the activity feed, `lib/comments.ts` and the permalink login round trip. Go: service tests, API tests for the role matrix, cross project access, escaping and limits, project token authors, SSE event and the feed (viewer never sees owner only audit rows, foreign project rows, paging).

### M5 implementation notes: CLI, GitHub Action, examples (5.4, 5.7)

CLI (`cmd/sandpost/ci.go`, `wait.go`, `extract.go`; HTTP in `internal/ciclient`)
- The commands are API clients, not server tasks: they never call `config.Load` (no `DATABASE_URL` or `SECRET_KEY`) and use the wait and extract routes with a project token (`Authorization: Bearer`). `internal/ciclient` validates what it can with the server's limits (count 1 to 50, timeout 0 to 120 s, run id rule, numeric project id) so a typo is a usage error before any request, and it keeps the token out of every error text.
- Configuration: flags with environment fallbacks (`SANDPOST_URL`, `SANDPOST_PROJECT`, `SANDPOST_RUN_ID`, then `GITHUB_RUN_ID`, `CI_PIPELINE_ID`, `BUILDKITE_BUILD_ID`, `CIRCLE_WORKFLOW_ID`). The token is environment only, like every secret of this binary (argv shows in `ps` and CI logs). The run id is sent as the `run` query parameter, never as the header. An explicit `--run=` turns the filter off. A CI variable that differs from what the application sends only causes a timeout (fail safe), but `GITHUB_RUN_ID` repeats on a re-run, so the docs tell to use `run_id-run_attempt` on both sides.
- Exit codes: 0, 1 (error), 2 (usage) as before, 3 timeout, 4 nothing to extract. `run()` maps a `*codedError` to its code (`errors.As`), any other error is 1. A timeout is the server's `timed_out: true` (always HTTP 200), so the CLI turns it into exit 3; `--json` still prints the partial answer first. Exit 4 exists so `CODE=$(sandpost extract)` can not carry on with an empty value.
- Output: only the value goes to stdout (ids, code or link, one per line), diagnostics go to stderr. `extract` has no single server call to rely on: it does wait (count 1) and extracts on the oldest match (`--latest`: the newest, the server lists oldest first, at most 200), or takes `--message`. Waiting options with `--message` are a usage error rather than silently ignored.
- The HTTP deadline is the poll timeout plus 15 s, so the server's own answer arrives before the client gives up. There is no retry: a connection error is exit 1 (a retry would need to be idempotent per `after_id`, which it is, but it was not asked for).
- Tests: `cmd/sandpost/ci_test.go` against a fake API (flags, env, run resolution, usage errors that must not reach the server, exit codes, token never printed), `internal/ciclient` with `httptest`, and `ci_e2e_test.go` runs the real server: SMTP in with `X-Run-Id`, `wait` released by mail that arrives later, run isolation (another run times out with exit 3), `extract` of code and link, bad token and foreign project.

GitHub Action (`action.yml` at the repository root, `.github/scripts/sandpost-action.sh`)
- Composite. There are no release binaries, so it runs `setup-go` and builds the CLI from `github.action_path` (the checkout of the action's own ref): the CLI always matches the action version, at the cost of a build per job (about a minute cold). Replace the build with a download when 6.1 publishes releases. It needs a Linux or macOS runner with bash and `jq`.
- `command: install` only puts the CLI on `PATH` (for the examples, where the test code calls it). `wait` and `extract` run it through the script, which receives every input as an environment variable (never expanded into the script text, so a query or a PR title can not inject shell), always runs the CLI with `--json`, writes `message-id`, `message-ids`, `value` and `json` to `$GITHUB_OUTPUT` and exits with the CLI's code, so a timeout fails the step while the outputs are still set. A value that is not a URL is masked with `::add-mask::` before anything prints it (one-time codes are secrets in a log).
- Verified locally with the real binary and a fake API (all outputs, timeout, bad command, shell metacharacters in the query). Not run on a GitHub runner, and not linted with actionlint (not installed).

Examples (`examples/jest`, `examples/pytest`, `examples/playwright`)
- Each is self contained: a stand-in "application" that sends mail over SMTP with `X-Run-Id`, a small helper that runs the CLI, a test, a README and `ci.example.yml` (outside `.github/workflows/` on purpose, it would run in this repository's CI). They use `sandpost extract` through the installed binary so the examples show the same contract as the docs.
- Syntax checked only (`node --check`, `py_compile`) and the two helpers were run against a fake API. The test suites were not run (no dependencies installed, no live server): treat them as unverified until a CI job runs them against a seeded Sandpost.

## 3. Data model (Postgres)

```
users(id, email, name, password_hash, is_admin, must_change_password, created_at, disabled_at)
groups(id, name, created_at)                          -- unique on lower(name)
group_members(group_id, user_id, added_at)
projects(id, slug, name, created_at)
project_groups(project_id, group_id, role)            -- role: viewer | member | owner

smtp_credentials(id, project_id, username, secret_hmac, label, created_at, revoked_at, last_used_at)
api_tokens(id, owner_user_id null, project_id null, token_hmac, prefix, label, scopes text[],
           created_by null, created_at, revoked_at, last_used_at)   -- exactly one of owner_user_id, project_id
sessions(id bytea = HMAC of the cookie value, user_id, created_at, expires_at)

messages(id, project_id, received_at, message_id_hdr, from_addr, subject, size_bytes,
         text_body, html_body, raw bytea, headers jsonb, read_at, search tsvector)
message_recipients(message_id, kind, address)         -- to | cc | bcc | envelope
attachments(id, message_id, filename, content_type, size_bytes, content_id, inline)
message_links(message_id, url)
tags(id, project_id, name)
message_tags(message_id, tag_id)
tag_rules(id, project_id, match, tag)                 -- header or recipient based
comments(id, project_id, message_id, user_id null, author_label, body, created_at)   -- see the M5 notes (comments)

transports(id, project_id unique, kind, host, port, username, secret_enc, tls_mode, sender, enabled, created_at, updated_at)
delivery_policies(project_id, mode, allowlist jsonb, redirect_address, subject_prefix)
deliveries(id, project_id, message_id, run, kind, recipient, effective_recipient, status, error, attempts,
           created_at, updated_at, sent_at)   -- unique (message_id, run, recipient), see the M4 notes

audit_log(id, at, actor_user_id, project_id null, action, target, detail jsonb)
```

Notes:
- `messages` is indexed on `(project_id, received_at DESC)` and has a GIN index on `search`. `pg_trgm` indexes on address and subject support partial matches.
- `raw` is TOASTed. Attachment bytes are not duplicated, they are read back out of `raw` on request. If this proves slow, a later blob store can be introduced behind an interface.
- Partitioning `messages` by `received_at` is deferred until retention is built, but IDs and indexes are chosen so it can be added.
- Row level security is considered as defense in depth for project tables, but the primary control is the scoped repository layer.

## 4. Key flows

**Send from an app**: connect, AUTH with project credential, `MAIL FROM`/`RCPT TO`/`DATA`, ingest transaction, `NOTIFY`, UI updates, policy runs async.

**CI waits for an email**: the pipeline sends mail, then calls `wait?to=user+run42@example.test&timeout=30s`. The server checks existing rows, then listens on the project channel until a match arrives or the timeout expires.

**Redirect delivery**: ingest commits, the policy job reads the message, splits recipients into allowed and redirected, builds two outbound messages (envelope rewritten, headers added), sends through the project transport, records each result.

## 5. Deployment

- Image: distroless static Go binary, non-root, config by env vars and an optional file.
- Required config: `DATABASE_URL`, `SECRET_KEY`, `SMTP_LISTEN`, `HTTP_LISTEN`, TLS cert paths (optional), `ADMIN_EMAIL`/`ADMIN_PASSWORD` for first boot bootstrap.
- Migrations run on start under an advisory lock, or as a separate `migrate` subcommand and Helm hook.
- Helm chart: Deployment, a Service of type `LoadBalancer` or `NodePort` for SMTP (TCP, not HTTP ingress), Ingress for HTTP, optional bundled Postgres for demos, ServiceMonitor for metrics.
- Health: `/healthz`, `/readyz`. Metrics: `/metrics` (Prometheus) with ingest rate, SMTP auth failures, delivery outcomes.

## 8. Decisions

Resolved:
1. Compatibility API is token-scoped on `/api/v1`, with an optional `/p/{slug}/api/v1` alias. The native API lives under `/_/api/v1`.
2. Job queue: River.
3. Machine credentials (SMTP secrets, API tokens) are server-generated and stored as HMAC-SHA256. Argon2id is used only for human passwords. No verification cache.
4. Sharing a message in v1 is a permalink that requires login and project access. There is no `share_links` table. Public signed links may come later as an opt-in per project.
5. SSE only, no WebSocket.
6. License: MIT. Module path: `github.com/sandpost-mail/sandpost`.
