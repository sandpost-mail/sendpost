# Sandpost

Self-hosted email capture and safe delivery for development, staging and CI. One Go binary, a Svelte UI, Postgres. See [docs/PRD.md](docs/PRD.md), [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md) and [docs/BACKLOG.md](docs/BACKLOG.md).

Status: early development. M1 (capture core) is done: apps send mail through authenticated SMTP and it is stored and streamed live. M2 (access control) is done: login, sessions, users, groups, project roles, API tokens and an audit log, with the whole native API behind them, and the web UI for login, administration, tokens and audit (see "Access control" below). M3 (Mailpit-compatible API) is implemented: tests written for Mailpit work against `/api/v1` with a project token (see "Mailpit-compatible API" below). Running real Mailpit client libraries against it is still to do. M4 (delivery policy) is implemented: optional outbound delivery through a per-project SMTP relay with an allowlist, redirect mode and manual release (see "Delivery policy" below).

## Quick start

Requirements: Go (see `go.mod`), Docker, Node 22 or later for the web app.

```
make dev        # builds the UI, Postgres in Docker, migrations, server on :8080 (SMTP :1025)
make dev-nodb   # same without Docker: needs DATABASE_URL pointing at your own Postgres
make test       # unit and integration tests (integration tests need Docker, or TEST_DATABASE_URL)
make lint
make web-check  # svelte-check; `cd web && npm test` runs the web unit and component tests
make openapi    # check docs/openapi.yaml against the routes and lint it (needs Node)
```

Run the full stack in containers:

```
cp deploy/.env.example deploy/.env   # then set SECRET_KEY (openssl rand -hex 32)
docker compose -f deploy/docker-compose.yml --env-file deploy/.env up --build
```

## Configuration

Environment variables, optionally preloaded from a `KEY=VALUE` file named by `SANDPOST_CONFIG_FILE` (environment wins over the file).

| Variable | Required | Default | Notes |
|---|---|---|---|
| `DATABASE_URL` | yes | | Postgres connection string |
| `SECRET_KEY` | yes | | at least 32 bytes |
| `SMTP_LISTEN` | no | `:1025` | |
| `HTTP_LISTEN` | no | `:8080` | |
| `TLS_CERT_FILE`, `TLS_KEY_FILE` | no | | set both or neither |
| `ADMIN_EMAIL`, `ADMIN_PASSWORD` | no | | first boot bootstrap, set both or neither. Creates an admin (password change required at first login) only when there are no users yet, never overwrites |
| `COOKIE_SECURE` | no | `true` | marks the UI session cookie `Secure` and uses the `__Host-` cookie name. Works over HTTPS (also behind a TLS terminating proxy) and on `http://localhost` in Chrome and Firefox. Set `false` only for plain http on another host name (for example a LAN address) or Safari on localhost. `make dev` and `make dev-nodb` default it to `false` |
| `MAX_MESSAGE_BYTES` | no | 26214400 | |
| `SMTP_TLS_MODE` | no | `off`, or `starttls` when a certificate is set | `off`, `starttls` (plaintext AUTH still allowed), `required` (AUTH only after STARTTLS), `implicit` (TLS from the first byte). Anything but `off` needs the certificate |
| `LOG_LEVEL`, `LOG_FORMAT` | no | `info`, `text` | format is `text` or `json` |

## Using it

1. Open the UI and sign in (first boot: `ADMIN_EMAIL` and `ADMIN_PASSWORD`, then choose a new password when asked). As an admin create a project, then Settings, Create credential. The secret is generated by the server and shown once, with a copyable `.env` snippet.
2. Point your app at the SMTP host and port with AUTH PLAIN or LOGIN. Unauthenticated `MAIL FROM` is refused, and the credential alone decides which project receives the mail.
3. Messages show up live in the project inbox (HTML in a sandboxed iframe with scripts and remote content blocked, text, source, headers, attachments, links).

Behavior worth knowing:
- Failed SMTP logins are limited per source IP (10 failures per 5 minutes, then 454 until they age out). Messages above `MAX_MESSAGE_BYTES` get 552.
- Search syntax in the inbox: `from:` `to:` `subject:` `tag:` `body:` `date:YYYY-MM-DD` `after:` `before:`, quoted values for spaces, plain words match subject and body.
- Tag rules (Settings) tag messages at ingest by header (for example `X-Run-Id` into `run:{value}`) or recipient, with `*` wildcards.
- Live updates use Postgres `LISTEN/NOTIFY` and SSE, so every replica pushes to its own browsers.
- Native API under `/_/api/v1`, described in [docs/openapi.yaml](docs/openapi.yaml). Writes must send `Content-Type: application/json`.

## Access control

Every native API route except login and the signed preview URLs needs authentication, either a browser session or an API token.

- In the UI: admins get an Admin menu (users, groups with members, audit log) and create projects. Project owners get Settings (SMTP credentials, tag rules, project API tokens, group roles) and the project Audit page. Everyone can manage their own API tokens and password under their name in the top bar. Actions a role does not allow are hidden, the server still enforces them.
- The first admin comes from `ADMIN_EMAIL` and `ADMIN_PASSWORD` and must change the password at first login. Admins create users and groups, assign groups to projects with a role (viewer, member or owner), and create projects. A user's role on a project is the highest role among its groups.
- Log in with `POST /_/api/v1/auth/login` (`{"email", "password"}`). The response sets the session cookie and returns a `csrf_token` that must be sent as `X-CSRF-Token` on every write. While `must_change_password` is true only `POST /auth/password`, `GET /auth/me` and logout work.
- For scripts and CI use API tokens: `POST /_/api/v1/users/me/tokens` (user token, `spu_...`) or `POST /_/api/v1/projects/{id}/tokens` (project token, `spp_...`, pinned to one project, scopes `read` and `write`). The secret is shown once, send it as `Authorization: Bearer <token>`. Tokens never exceed what their owner may do and can be revoked.
- A project you have no role on answers 404, exactly like a project that does not exist. A visible project where your role is too low answers 403.
- Admin actions are recorded in an audit log: `GET /_/api/v1/audit` for admins, `GET /_/api/v1/projects/{id}/audit` for project owners.

Plain http note: with the default `COOKIE_SECURE=true` the session cookie is only stored by clients that treat the origin as secure, which includes `http://localhost` in Chrome, Firefox and recent curl, but not Safari or `http://<lan-address>`. Use HTTPS, or set `COOKIE_SECURE=false` for such setups.

```
curl -c jar -H 'Content-Type: application/json' -d '{"email":"admin@example.com","password":"..."}' localhost:8080/_/api/v1/auth/login
curl -b jar -H 'Content-Type: application/json' -H "X-CSRF-Token: $CSRF" -d '{"name":"Shop"}' localhost:8080/_/api/v1/projects
```

## Mailpit-compatible API

An existing per-project Mailpit setup moves to Sandpost by changing the base URL and the credential. The API of Mailpit v1.31.6 is served, project-scoped, at `/api/v1` (project token) and `/p/{project-slug}/api/v1` (project token, or a user token with a role on the project): list, search, get message, raw, headers, attachments, `/view/{id}.html|.txt`, delete, mark read and tags. Send the token as `Authorization: Bearer <token>`, or as the password of HTTP Basic auth with any username.

```
curl -u x:$SANDPOST_TOKEN 'localhost:8080/api/v1/search?query=to:user@example.test&limit=5'
```

Reads need the `read` scope, delete and tag changes need `write`. Message ids are decimal strings. Release works with a transport and an allowlist (see Delivery policy). Not supported (answers 501): send, chaos, HTML/link/spam checks, thumbnails. See [docs/MAILPIT_COMPATIBILITY.md](docs/MAILPIT_COMPATIBILITY.md) for the endpoint matrix, the search syntax and the deviations, and [docs/MAILPIT_MIGRATION.md](docs/MAILPIT_MIGRATION.md) for the migration steps. The vendored contract is in [docs/mailpit](docs/mailpit).

## Delivery policy

Off by default: Sandpost only captures mail. A project owner can add one outbound SMTP relay (Settings, Delivery: generic SMTP or Amazon SES SMTP) and a policy:

- **Capture only** (default): nothing is ever sent.
- **Allow**: recipients on the allowlist (addresses or whole domains such as `@example.com`) get the mail for real, the others get nothing.
- **Redirect**: allowlisted recipients get the mail for real, every other recipient is replaced by one redirect address. The original recipients are kept in `X-Original-To` and `X-Original-Cc`, the subject can get a prefix.

The envelope is rewritten, not only the headers, `Bcc` is never sent, and allowed and redirected recipients are delivered as separate messages. A copy always stays in Sandpost. Anything unclear fails closed: a missing or disabled transport, an invalid allowlist entry or redirect address, an unparsable recipient, a password that can not be decrypted: nothing is sent, and the Delivery tab of the message says why. A new transport starts disabled, and changing its host, port, user, encryption or type disables it again and asks for the password again. Certificates are always verified and a password is never sent without TLS.

The relay password is encrypted at rest with a key derived from `SECRET_KEY`. After changing `SECRET_KEY`, owners have to enter their relay passwords again. Delivery runs as jobs on [River](https://github.com/riverqueue/river) (Postgres backed, MPL-2.0, used unmodified): up to 5 attempts, with a status per recipient. `sandpost migrate up` also creates River's tables.

A message can also be released manually to specific addresses (message page, Delivery tab, or Mailpit's `POST /api/v1/message/{ID}/release`). Every target must be on the allowlist and the transport must be enabled. Settings need the owner role, a release needs member, the delivery status of a message needs viewer. See ARCHITECTURE for the details.

## Commands

`sandpost serve`, `sandpost migrate [up|down|status]` (up also applies River's job queue migrations, down only rolls back Sandpost's own), `sandpost admin`.

### Account recovery (`sandpost admin`)

Run on the server with direct database access (`DATABASE_URL` and `SECRET_KEY`, loaded like `serve`), with Docker Compose `docker compose -f deploy/docker-compose.yml --env-file deploy/.env exec app /sandpost admin ...` (add `-T` when piping a password with `--password-stdin`). This is how a locked out last administrator recovers.

| Command | Effect |
|---|---|
| `sandpost admin list-users` | list users (id, email, admin, disabled, must change password) |
| `sandpost admin create-admin <email> [--name N]` | create an administrator, password change required at first login |
| `sandpost admin reset-password <email>` | set a new password, require a change at next login, end all of the user's sessions |
| `sandpost admin unlock <email>` | enable a disabled user (clears `disabled_at`) |
| `sandpost admin promote <email>` | make the user an administrator |

Passwords are read from a prompt without echo (asked twice), or from the first line of stdin with `--password-stdin`, never from arguments. Example: `printf '%s\n' "$NEW_PASSWORD" | sandpost admin reset-password a@example.com --password-stdin`. Every change is written to the audit log with no user actor and `"actor": "cli"` in its detail. Login rate limits are kept in memory only, so they are not stored in the database: restart the server to clear them.
